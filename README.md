# Daily Stylist

Телеграм-бот, который ежедневно будет присылать рекомендацию одежды на основе вашего гардероба и погоды.

Статус: в разработке, MVP ещё не собран.

---

## Возможности

**MVP (сейчас делается)**

- **Онбординг.** Пока в гардеробе нет верха, низа, обуви и верхней одежды, приложение проводит через три шага: город, первые вещи - через обычную форму, с фотографией и распознаванием, - и время утренней рассылки. В конце сразу показывает первый образ.
- **Гардероб.** Вещи добавляются, редактируются и удаляются вручную. У каждой вещи есть статус: доступна, грязная, в архиве. Вещи не по сезону приложение отмечает само. Есть поиск и фильтры: не по сезону, надето, грязное, в архиве.
- **Утренняя рекомендация.** Приходит в заданное пользователем время, с учётом его часового пояса. Время, город и сам тумблер рассылки - за шестерёнкой на главном экране Mini App; по умолчанию 7:00.
- **Рекомендация по запросу.** По нажатию кнопки, несколько вариантов на выбор; любую вещь в варианте можно заменить.
- **Правка образа.** Вещь в варианте подбора и в образе дня можно заменить на другую из той же категории: список отсортирован по тому, насколько вещь подходит по погоде, и в нём есть поиск. Образ дня можно собрать и целиком руками.
- **Погода.** Для города, определённого по геопозиции или найденного по названию.
- **Учёт погоды и гардероба в подборе.** Температура, осадки и ветер, частота ношения (стараемся не повторяться), сочетаемость цветов, аксессуары: зонт, очки, сумка.
- **Много пользователей.** У каждого свой гардероб и свои настройки, чужие вещи недоступны.
- **Распознавание одежды на фотографии.** Форма сама заполняет то, что удалось узнать: что за вещь, цвета, сезоны, теплоту. Человек проверяет и правит.

**Планируется**

- подстройка под пользователя: одеваться теплее или легче - настройкой и кнопками «было холодно» / «было жарко», любимые и нелюбимые вещи - по тому, что человек надевает и заменяет;
- уточнение образа словами через GigaChat: «на собеседование», «весь день в офисе»;
- коллаж из фотографий вещей - увидеть образ целиком;
- советы по стилю и подсказки, что докупить в гардероб;
- уведомления о резкой смене погоды с предложением переодеться.

## Стек

| Часть | Технология |
|---|---|
| Бот, бизнес-логика, работа с базой | Go |
| Mini App: добавление и просмотр гардероба | React |
| Хранилище | PostgreSQL |
| Фотографии вещей | SeaweedFS, доступ по протоколу S3 |
| Погода и города | Open-Meteo, OpenStreetMap Nominatim |
| Кэш погоды, лимит распознаваний | Redis |
| Распознавание одежды | GigaChat, запрос из Go |
| Своя модель распознавания и коллаж | Python + gRPC, отдельный сервис, Marqo FashionCLIP в ONNX Runtime |

Распознавателей два, и они настраиваются: основной и запасной на случай, когда у основного кончились токены. GigaChat вызывается прямо из бота, своя модель работает в отдельном сервисе на Python - там же появится коллаж.

Своя модель - [Marqo FashionCLIP](https://huggingface.co/Marqo/marqo-fashionCLIP): CLIP, дообученный на фотографиях одежды. Она не описывает снимок словами, а сравнивает его с заранее заготовленными подписями вроде «фото куртки» и выбирает самую похожую; если уверенности не хватает, поле остаётся пустым. Цвета считаются отдельно, по пикселям. Работает на процессоре и токенов не тратит, но угадывает меньше GigaChat: категорию - хорошо, теплоту и непромокаемость - хуже.

## Структура

```
backend/                  # Go: бот, логика, база
├── cmd/                  # точки входа - по одной на процесс
│   ├── bot/              #   слушает Telegram
│   ├── migrate/          #   накатывает и откатывает миграции
│   └── scheduler/        #   утренняя рассылка по расписанию
├── internal/
│   ├── config/           # настройки из переменных окружения
│   ├── domain/           # сущности и правила подбора одежды
│   ├── service/          # сценарии приложения и объявления портов
│   ├── adapter/          # реализации портов: postgres, хранилище фото, погода, vision
│   └── telegram/         # всё, что видит пользователь: хендлеры бота, API Mini App, тексты
└── migrations/           # SQL-миграции

frontend/                 # React: Mini App для гардероба
vision/                   # Python: распознавание одежды на фотографии (коллаж - позже)
contracts/                # vision.proto - договор между Go и Python
deploy/                   # docker-compose: postgres, хранилище фото, распознавание, redis, бот, планировщик
docs/                     # решения по архитектуре и причины, по которым они приняты
```

Зависимости направлены внутрь: `domain` не знает ни о ком, `service` знает только о `domain`, а `adapter` и `telegram` знают о `service`, но не наоборот. Связывает всех точка входа в `cmd/bot`.

Тесты лежат рядом с кодом, который проверяют; отдельной папки для них нет.

## Предполагаемая архитектура на выходе

![Целевая архитектура: бот, планировщик, очередь задач и отправщик](assets/architecture-target.png)

В MVP есть всё, кроме очереди: бот одним процессом - вебхук, API Mini App и подбор, - планировщик рядом вторым, PostgreSQL, Redis, хранилище фотографий и распознавание. Распознавание вызывается синхронно, по gRPC: пользователь всё равно ждёт ответа, очередь только добавила бы ожидание.

Очередь разделит утреннюю рассылку надвое: планировщик будет только ставить задачи, а отправщик - разбирать их, собирать образ и слать сообщение. Тогда рассылку можно ускорить, добавив отправщиков, а сообщение, не ушедшее с первого раза, повторить.

## Разработка

Нужны Go 1.27+, Node.js 20.19+, Docker и [ngrok](https://ngrok.com/).

### Первый запуск

1. Скопируйте настройки и впишите в `backend/.env` токен бота и секрет вебхука:

   ```bash
   cp backend/.env.example backend/.env
   ```

2. Установите зависимости фронтенда:

   ```bash
   cd frontend && npm install
   ```

### Запуск

Все команды - из корня репозитория. Сначала поднимите базу, она работает в фоне:

```bash
docker compose --env-file backend/.env -f deploy/docker-compose.yml up -d --wait
```

Логин, пароль и порт базы compose берёт из `backend/.env`, а `DATABASE_URL` там собирается из них же. Данные переживают перезапуск контейнера.

Вместе с базой поднимается [SeaweedFS](https://github.com/seaweedfs/seaweedfs) - хранилище фотографий вещей с доступом по протоколу S3. Ключи и порт он тоже берёт из `backend/.env`, а бакет `S3_BUCKET` создаётся сам при первой загрузке файла. Посмотреть, что в нём лежит, можно в файловом браузере: http://localhost:58888.

И Redis - в нём кэш прогноза погоды и счётчик распознаваний через GigaChat. Бот и планировщик без него не запускаются, но если он упадёт уже во время работы, погода просто пойдёт мимо кэша. Адрес - `REDIS_URL` в `backend/.env`.

Для распознавания одежды на фотографии по умолчанию используется GigaChat, которому нужен ключ: впишите `GIGACHAT_AUTH_KEY` в `backend/.env`, иначе бот не запустится и скажет об этом. Отдельный контейнер для этого не нужен - в облако бот ходит сам.

Сервис со своей моделью вместе с базой не поднимается: образ с ней весит около 400 МБ, и модель скачивается с Hugging Face при его сборке. Он нужен, только если поставить `RECOGNIZER=vision` или `RECOGNIZER_FALLBACK=vision`, и поднимается отдельно:

```bash
docker compose --env-file backend/.env -f deploy/docker-compose.yml --profile vision up -d --wait vision
```

Затем накатите миграции. Бот сам этого не делает и без них не запустится:

```bash
(cd backend && go run ./cmd/migrate up)
```

Подробнее - в разделе [«Миграции»](#миграции).

Дальше понадобятся три терминала. Начинайте с туннеля: его адрес нужен остальным.

1. Туннель на фронтенд:

   ```bash
   ngrok http 5173
   ```

   Скопируйте адрес из строки `Forwarding` и впишите его в `backend/.env`:

   ```
   TELEGRAM_WEBHOOK_BASE_URL=https://xxxx.ngrok-free.app
   ```

   Этот же адрес бот подставляет в ссылки на фотографии: `S3_PUBLIC_URL` в `.env.example` собирается из него.

2. Бэкенд. Запускается из папки `backend/`, иначе не найдёт `.env`:

   ```bash
   cd backend && go run ./cmd/bot
   ```

3. Фронтенд:

   ```bash
   cd frontend && npm run dev
   ```

   Утренняя рассылка - отдельный процесс, боту он не нужен: `make sched`. Без него рекомендация по кнопке работает, а утром сама не приходит. Адрес туннеля ему тоже нужен: из него собирается кнопка «Ещё варианты» под сообщением.

4. В @BotFather: `/mybots` → ваш бот → Bot Settings → Menu Button → Configure menu button. Отправьте адрес туннеля, затем название кнопки, например «Гардероб».

Откройте чат с ботом и нажмите кнопку меню. Или напишите боту что угодно: он поздоровается и подскажет, куда нажать. Посмотреть добавленные вещи можно в консоли базы:

```bash
docker compose --env-file backend/.env -f deploy/docker-compose.yml exec postgres sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB"'
```

и в ней `SELECT id, user_id, name, category FROM items;`.

Как это связано: снаружи виден только туннель на Vite (порт 5173). Vite отдаёт страницу Mini App, запросы к `/api` и `/telegram` пересылает Go-серверу на порт 2000, а запросы к `/photos` - в хранилище на порт 58333. Фотографии идут мимо бота: он только выдаёт браузеру подписанные ссылки, по которым тот сам кладёт и забирает файлы.

### Если что-то не работает

- **Бот пишет «не заданы обязательные переменные окружения: REDIS_URL».** `backend/.env` скопирован до появления Redis: возьмите строки `REDIS_*` и `TEST_REDIS_URL` из `backend/.env.example` и заново выполните `make db`.

- **Адрес ngrok меняется при каждом перезапуске.** Обновите `TELEGRAM_WEBHOOK_BASE_URL`, перезапустите бэкенд и заново укажите адрес в BotFather. Чтобы не делать этого каждый раз, возьмите в ngrok бесплатный постоянный домен.
- **ngrok показывает страницу-предупреждение.** Нажмите «Visit Site».
- **Бот пишет «есть непримененные миграции».** После `git pull` появились новые миграции: выполните `(cd backend && go run ./cmd/migrate up)`.
- **Фотография не загружается, а в консоли браузера ошибка 403.** Адрес туннеля сменился, а `S3_PUBLIC_URL` остался старым: подпись ссылки считается от адреса и со старым не сходится. Обновите `TELEGRAM_WEBHOOK_BASE_URL` и перезапустите бэкенд.
- **Фотография загрузилась, но поля формы остались пустыми.** Либо модель не узнала вещь, либо кончились токены GigaChat, либо пользователь за сутки распознал больше 50 фотографий - дальше GigaChat не зовётся, либо не поднят сервис со своей моделью. Что именно - видно в логе бота. Форма в любом случае молчит: заполнить поля руками можно всегда. Проверить, что до GigaChat вообще достучаться: `make check-gigachat` (тратит токены).
- **`make check-db` пишет `database "stylist_test" does not exist`.** Том базы создан раньше, чем появился скрипт, который её создаёт. Один раз выполните в `make psql`: `CREATE DATABASE stylist_test;`.

### Миграции

Схемой базы управляет [goose](https://github.com/pressly/goose). Миграции - SQL-файлы в `backend/migrations/`, в каждом секции `-- +goose Up` (как применить) и `-- +goose Down` (как отменить). Бот сам миграции не накатывает: при старте он только проверяет, что применены все, и иначе не запускается.

Применять и откатывать можно двумя способами, результат одинаковый: версию базы оба хранят в таблице `goose_db_version`.

**Через `cmd/migrate`.** Ставить ничего не нужно, миграции встроены в бинарник. Так же они будут применяться на сервере.

```bash
cd backend
go run ./cmd/migrate status        # какие применены, какие нет
go run ./cmd/migrate up            # накатить все новые
go run ./cmd/migrate up-to 3       # накатить до версии 3 включительно
go run ./cmd/migrate down          # откатить последнюю
go run ./cmd/migrate down-to 0     # откатить до версии 0, то есть все
```

Частые команды есть в Makefile: `make migrate`, `make migrate-status`, `make migrate-down`.

**Через goose CLI.** Умеет то же самое, и только им создаются файлы новых миграций. Ставится один раз, той же версии, что в `go.mod`:

```bash
go install -tags='no_clickhouse no_libsql no_mssql no_mysql no_sqlite3 no_vertica no_ydb' github.com/pressly/goose/v3/cmd/goose@v3.28.0
```

Теги отключают драйверы других баз, иначе сборка заметно дольше. Из папки `backend/` goose сам берёт подключение и папку миграций из `.env` (переменные `GOOSE_*`):

```bash
cd backend
goose -s create add_brand sql      # новый файл migrations/0000N_add_brand.sql
goose status
goose up
goose down
```

Файл миграции можно создать и через `make migration name=add_brand`. Флаг `-s` даёт номера `00001`, `00002` вместо даты и времени в имени.

### Проверки

Бэкенд. Линтер ставится один раз, той же версии, что в CI:

```bash
go install github.com/golangci/golangci-lint/v2/cmd/golangci-lint@v2.13.2
```

Дальше проверка занимает секунды:

```bash
(cd backend && go test ./... && golangci-lint run --build-tags integration)
```

Тесты адаптеров Postgres и хранилища помечены тегом `integration` и без базы не запускаются. Работают они в отдельной базе `stylist_test` в том же контейнере, рабочие данные не видят. Проще всего `make check-db`: адрес он берёт из `TEST_DATABASE_URL` в `backend/.env`. Вручную, с поднятой базой:

```bash
(cd backend && TEST_DATABASE_URL=<адрес базы> go test -count=1 -tags integration ./internal/adapter/postgres/)
```

Так же устроены тесты хранилища: `make check-s3` гоняет их в отдельном бакете `photos-test` из `TEST_S3_BUCKET`, рабочие фотографии они не видят. Фейком эти тесты не заменить: проверяют они как раз то, принимает ли живое хранилище подписанные ссылки - с привязанными размером и типом файла и без подписи.

И тесты Redis: `make check-redis` гоняет их в отдельной базе номер 1 из `TEST_REDIS_URL`, рабочие ключи они не видят.

`-count=1` отключает кэш результатов: без него Go покажет `ok (cached)`, даже если база выключена, потому что код с прошлого запуска не менялся.

Со значениями из `backend/.env.example` адрес - `postgres://stylist:stylist@localhost:55432/stylist_test`.

Внутри неё каждый тест создаёт себе отдельную схему и удаляет её после себя, так что тесты не мешают друг другу.

Тесты с детектором гонок (`go test -race`) заметно медленнее - их гоняет CI.

Сервис со своей моделью. Окружение создаётся один раз - `make vision-venv`; тесты в сеть не ходят и модель не грузят, они проверяют цвета по пикселям, выбор подписи и сам gRPC-сервер на заглушке:

```bash
make check-vision
```

Эти же проверки гоняет CI.

Если правится `contracts/vision.proto`, код для Go и Python перегенерируется командой `make proto`. Ей нужны плагины protoc тех же версий, что в CI, они ставятся один раз:

```bash
go install google.golang.org/protobuf/cmd/protoc-gen-go@v1.36.10
go install google.golang.org/grpc/cmd/protoc-gen-go-grpc@v1.5.1
```

Сам protoc ставить не нужно: он приезжает с пакетом `grpcio-tools` в окружении `vision/.venv`.

Сгенерированный код лежит в репозитории, и отдельный воркфлоу CI повторяет `make proto` и падает, если результат разошёлся с закоммиченным. Сам по себе рассинхрон почти ничем себя не выдаёт: у Go он ломает сборку, только когда код уже обращается к новому полю, у Python молчит до рантайма.

Живой запрос к GigaChat проверяется отдельно и тратит токены, поэтому в `make check` не входит:

```bash
make check-gigachat
```

Посмотреть, как модель разбирает конкретный снимок: `GIGACHAT_TEST_PHOTO=/путь/к/фото.jpg make check-gigachat`.

Фронтенд - типы, сборка и линтер:

```bash
(cd frontend && npm run build && npm run lint)
```
