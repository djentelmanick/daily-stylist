# Daily Stylist — архитектура

Документ фиксирует принятые решения и **причины** этих решений. Причины важнее самих решений: когда через полгода захочется что-то поменять, нужно понимать, какое соображение при этом ломается.

Что делает продукт — в `PRODUCT.md`.

Дата: 2026-09-10.

---

## 1. Стек

| Часть | Технология |
|---|---|
| Бот + бизнес-логика + база | Go |
| Mini App: добавление и просмотр гардероба | React |
| Хранилище | PostgreSQL |
| Состояние диалогов, кэш погоды | Redis |
| Работа с картинками (распознавание, коллаж) | Python + FastAPI, отдельный сервис |

### Почему бот на Go, а не на Python

Отказались от aiogram, который дал бы из коробки конечный автомат диалогов и хранилище состояний.

Причина: в телеграм-боте слой хендлеров — **это весь пользовательский интерфейс**, а не тонкая прослойка. Там живут онбординг, редактирование вещи, подтверждение распознанных кандидатов, настройки времени рассылки. Если UI на Python, а логика на Go, то каждое нажатие кнопки становится сетевым вызовом, а каждая сущность существует в двух языках и расходится при первом изменении. Разовая экономия на конечном автомате этого не окупает.

С появлением Mini App часть UI — добавление и просмотр вещей — переехала в React. Почему это не возвращает проблему «сущность в двух языках», объяснено в разделе 7.

**Признак хорошего места для разреза по языкам:** узкий и редко меняющийся контракт. У распознавания он такой (`байты → список кандидатов`). У UI — нет.

### Почему vision вынесен отдельно

Другой профиль ресурсов (память под модель, возможно GPU), другой темп деплоя (модель обновляется чаще кода), плюс Pillow приятнее для коллажа, чем `image/draw`.

Распознавание и коллаж живут в **одном** сервисе, а не в двух: оба stateless, оба про картинки, оба CPU-тяжёлые.

Больше не выносится ничего. Рекомендатор ходит только в свою же базу, гардероб — обычный CRUD, погодный клиент — HTTP-запрос с кэшем. Сетевой хоп добавил бы им задержку и не дал взамен ничего.

Два правила для этого сервиса:

- он **не ходит в Postgres** и **не знает про Telegram**. Go скачивает файл у Telegram и передаёт байты. Сервис остаётся чистой функцией и тестируется без инфраструктуры;
- на MVP связь — **синхронный HTTP с таймаутом**, не очередь. Пользователь и так ждёт ответа. Очередь появится, когда будет реальная причина: батчинг, ретраи, холодный старт модели.

Контракт — `contracts/openapi.yaml`, из него генерируется Go-клиент. Рассинхрон становится ошибкой компиляции, а не багом в проде.

## 2. Порты и адаптеры

Логика ни от кого не зависит — она сама объявляет, что ей нужно:

```
        telegram/                adapter/postgres, weather, vision
       (входящий)                        (исходящие)
            │                                  │
            ▼                                  ▼
        service/  ────────  ports.go  ◄────────┘
            │            (интерфейсы объявлены здесь)
            ▼
        domain/
```

Ключевое требование: интерфейс объявлен **в `service/`**, рядом с тем, кто им пользуется, а не рядом с реализацией. Реализация пакет с интерфейсом даже не импортирует — в Go интерфейсы реализуются неявно.

### Порт говорит на языке ядра, а не провайдера

Порт описывает потребность рекомендателя, адаптер переводит на неё чужой формат:

```go
Forecast(ctx context.Context, location domain.Location, from, to time.Time) (domain.Weather, error)
```

`Weather` — свой тип с полями, которые нужны логике. Если бы порт возвращал ответ погодного API как есть, зависимость была бы развёрнута только формально: ядро всё равно разбирало бы JSON конкретного провайдера, и при смене поставщика правки поползли бы внутрь.

Порты держим узкими: ровно те методы, которые реально вызываются.

### Какие порты заводим

Порт окупается там, где за ним что-то неконтролируемое, мешающее тестам:

- **погода** и **vision** — сеть;
- **`Clock`** — недетерминизм. Обязателен: утренняя рассылка с таймзонами без него не тестируется;
- **отправка сообщения в Telegram** — внешний эффект.

**Когда заводить новый:** когда реально мешает — пишешь тест и упираешься в сеть или время. Порт, добавленный заранее, почти всегда описывает не ту потребность, потому что настоящая ещё не проявилась.

**Что портом не оборачиваем:** приём апдейтов из Telegram. Это входящий адаптер, он и так снаружи, а «вдруг добавим Discord» не случится.

## 3. Репозитории и транзакции

### Репозитории под сценарий

Не универсальный `Find(criteria)`, а методы под конкретную потребность:

```go
AvailableFor(ctx context.Context, userID int64, season Season) ([]Item, error)
MarkWorn(ctx context.Context, itemIDs []int64, at time.Time) error
```

Универсальный интерфейс вырождается либо в «загрузить всё и отфильтровать в памяти», либо в пересказ SQL другими словами.

И честно: эти интерфейсы существуют **ради тестов**, а не ради смены СУБД. База не сменится. Понимая это, не жертвуем ради них производительностью.

### Транзакций в MVP нет — так спроектировано

«Создать образ и отметить вещи надетыми» требовало бы транзакции, если бы надетость была отдельным полем (`wear_count`, `last_worn_at`). Мы храним факт ношения строками в `outfit_items`: запись образа дня — **один** SQL-запрос (образ и его вещи вставляются через `WITH`), а «когда носил в последний раз» и «сколько раз» — запросы к этой таблице. Транзакция исчезает, а бонусом остаётся история вместо счётчика — она и так нужна для фидбека «надел не это» и для правила «не повторяться».

Общее соображение за этим решением: транзакция часто оказывается симптомом того, что одно знание хранится в двух местах.

**Если атомарность всё-таки понадобится:** логика не получает `*sql.Tx` — иначе `database/sql` вернётся в ядро. Она складывает шаги в функцию и отдаёт исполнителю «выполни целиком или не выполняй вовсе»; тот открывает транзакцию, запускает пакет, фиксирует или откатывает. Требование «это неделимо» остаётся бизнес-правилом в `service/`, механизм BEGIN/COMMIT — в адаптере.

Цена приёма: репозитории узнают о транзакции по пометке в `context`, компилятор эту связь не проверяет. Дисциплина — ни один репозиторий не открывает транзакцию сам, доступ к базе только через единую точку, плюс интеграционный тест «внутри пакета вернули ошибку → в таблице пусто».

Первый кандидат на такой пакет — лимит вещей в `service/wardrobe.go`: подсчёт и вставка — два разных запроса, и два одновременных добавления могут оба уложиться в лимит. Пока это отмечено TODO.

### Postgres в адаптере

- **Драйвер — pgx v5 в собственном интерфейсе, а не через `database/sql`.** Ценность `database/sql` — возможность сменить драйвер, а база у нас не сменится. Родной интерфейс pgx умеет массивы Postgres: сезоны и дополнительные цвета кладутся в `text[]` без обёрток.
- **SQL пишется руками, без sqlc.** Сравнивали на том же репозитории. sqlc ловит опечатку в SQL при генерации, но сам выбирает типы полей, и каждое доменное значение пришлось бы переводить в `string` или `int16`. Голый pgx принимает доменные типы-строки напрямую. На единицах запросов генератор не окупает лишний шаг сборки. Цена — ошибку в SQL видно только при выполнении, поэтому у адаптера обязательны интеграционные тесты, и CI их гоняет. Если запросов станет десятки, sqlc добавляется без изменения порта.
- **Во вставке — именованные аргументы (`@name`), а не `$1…$10`.** Позиционные связываются с колонками по порядку: поменяй местами название и описание — обе строки, база молча запишет не туда. Отдельный тест сверяет каждую колонку после вставки.
- **Перечисления — `text` без `CHECK`.** Иначе список значений жил бы в третьем месте после констант и `allCategories`, и каждый новый цвет требовал бы миграции. От мусора защищает `Validate`: при создании вещи и при чтении из базы.
- **Сезоны и дополнительные цвета — массивы, а не отдельные таблицы.** Они не существуют без вещи и всегда читаются вместе с ней. pgx записывает `nil`-срез как `NULL`, поэтому адаптер подставляет пустой.
- **Один пул соединений на процесс.** Создаётся в `cmd/bot` и раздаётся адаптерам. `pgxpool.New` к базе не подключается, поэтому сразу после него — `Ping`: недоступная база роняет бота при старте, а не на первом запросе пользователя.
- **Миграции — goose, SQL-файлы в `backend/migrations/`. Применяются отдельной командой `cmd/migrate`, а не при старте бота.** Если бот мигрирует сам, управлять версией схемы нельзя: откатил миграцию — перезапуск бота накатит её обратно. К тому же долгая миграция задерживала бы старт, а боту понадобились бы права менять схему. Миграции встроены в бинарник `cmd/migrate`, поэтому на сервер не нужно везти goose и папку с SQL, а миграции всегда из того же релиза, что и код. Блокировка в базе не даёт двум запускам применять миграции одновременно. goose CLI умеет то же самое, и файлы новых миграций создаются им.
- **Бот при старте проверяет, что все миграции применены, иначе не запускается.** Без проверки забытая миграция всплыла бы ошибкой на первом запросе пользователя.
- **Откат (`down`) — для разработки.** Он удаляет колонки вместе с данными, поэтому ошибку в проде исправляют новой миграцией. Применённую миграцию не редактируют: goose помнит только номер, и у разных баз с одной версией оказались бы разные схемы.
- **Локальная база — `deploy/docker-compose.yml`, настройки — из `backend/.env`.** Логин, пароль и порт лежат там один раз, а `DATABASE_URL` собирается из них подстановкой `${...}`: иначе одни и те же значения жили бы в двух местах и разошлись бы при первой правке. В compose остаются значения по умолчанию на случай, если файла нет. Бот при этом по-прежнему читает только `DATABASE_URL`, на сервере его можно задать целиком.

### Три правила, ради которых эта структура существует

1. `domain/` не импортирует ничего, кроме себя и стандартной библиотеки. Появился там `database/sql` или пакет телеграма — слой протёк.
2. `service/` импортирует только `domain/`. Все связи с внешним миром — через интерфейсы в `ports.go`.
3. `adapter/` и `telegram/` знают про `service/`, но `service/` про них — никогда. Знакомит всех `cmd/bot/main.go`.

### Что создавать сразу, а что нет

Под MVP нужны: `domain/`, `service/` (без распознавания), `adapter/postgres`, `adapter/openmeteo`, `telegram/`, `migrations/`.

Папки `vision/`, `adapter/vision/`, `contracts/` **не создавать заранее** — завести в день, когда туда пишется первая настоящая строка. Пустые каталоги «на будущее» превращаются в мусор, а заглушки-интерфейсы описывают не ту потребность.

### Тесты

Лежат рядом с кодом, отдельной папки `tests/` нет. Основной вес — на `domain/rules/` (чистые функции) и `service/` (сценарии на фейках портов). Фикстуры — в `testdata/` рядом с тестом. Тесты адаптера `postgres`, которым нужна живая база, помечаются тегом сборки `integration`, чтобы `go test ./...` работал без неё. Базу им указывает только `TEST_DATABASE_URL`, адрес бота (`DATABASE_URL`) тесты не берут никогда — ни сами, ни через `make check-db`. Локально это отдельная база `stylist_test` в том же контейнере, её создаёт скрипт инициализации compose. Так тесты физически не дотянутся до рабочих данных, даже если в `backend/.env` окажется чужой `DATABASE_URL`. Внутри базы каждый тест создаёт себе отдельную схему и накатывает в неё миграции, поэтому тесты не мешают друг другу. В CI база поднимается сервисом GitHub Actions.

## 5. Что заложено с самого начала

Границы MVP — в `PRODUCT.md`. Здесь только то, что переделывать дорого, поэтому учтено сразу:

- **Часовые пояса.** Рассылка «в 7 утра» без таймзоны сломается на первом же пользователе из другого пояса. Планировщик обязан быть идемпотентным: перезапуск не должен слать дубли.
- **Статус вещи — перечисление, а не флаг доступности.** Доступна / грязная / в архиве. Флаг пришлось бы расширять миграцией и правкой всех запросов. Почему значения именно такие — в разделе 6.
- **Фидбек отделён от факта ношения.** Рекомендация ≠ надетое. Без этого разделения частота ношения считается неверно, а на ней держится правило «не повторяться».
- **Кэш погоды и лимиты на распознавание.** Иначе упрёмся в квоты бесплатных API.

## 6. Модель вещи

Вещь описана в `domain/item.go`. Здесь — почему поля устроены именно так.

### Что в вещи есть, а чего нет

Поля: владелец, название, описание, категория, цвета, сезоны, уровень теплоты, непромокаемость, статус.

Описание необязательное: название говорит, что это за вещь, а описание — какая именно (фасон, где куплена, чем отличается от похожей). Название — до 30 символов, описание — до 60: в рекомендации вещь занимает одну строку, и длинные подписи раздули бы сообщение. Считаются символы, а не байты, иначе кириллица расходовала бы лимит вдвое быстрее. Лимиты приходят в Mini App из API, чтобы форма не разошлась с доменом.

- **Только то, чем пользуются правила.** `created_at` — колонка в таблице, она помогает разбираться с данными, но не поле доменной структуры: ни одно правило подбора на время создания не смотрит. `updated_at` не заводим, пока нет потребности: его пришлось бы поддерживать при каждом изменении.
- **Никаких тегов `json` и `db`.** Домен не знает, как вещь хранится и передаётся. Перевод в строку таблицы и обратно — работа адаптера.
- **Счётчика носки нет** — он считается из `outfit_items` (раздел 3).
- **Статуса «надета сейчас» нет.** Это образ на сегодня, и он уже записан в `outfit_items`. Второе место хранения того же знания рано или поздно разойдётся с первым.
- **Идентификаторы — `int64`.** В Postgres это `bigint`, а размер `int` зависит от платформы.

### Перечисления — строки

Категория, цвет, сезон и статус — отдельные типы на основе `string`, а не числа через `iota`. Значения попадают в базу, а номера из `iota` сдвигаются, если вставить новое значение в середину списка, — и старые записи молча меняют смысл. Строку видно в таблице и в логе, а пустая строка сама по себе невалидна.

Go не мешает написать `ItemStatus("мусор")`, поэтому у каждого перечисления есть `Valid()`. Значения при этом перечислены второй раз — в списках вроде `allCategories`: настоящих перечислений в Go нет, и без генерации кода этого повтора не избежать. Списки стоят сразу под константами, чтобы их было легко держать в согласии. Как проверяется вещь целиком — в конце раздела.

Исключение — уровень теплоты, о нём ниже.

### Категория — место в образе

Категория отвечает на один вопрос: какое место вещь занимает в образе. Рекомендатель собирает образ по местам — верх, низ, верхняя одежда, обувь, — поэтому список плоский. Подкатегория имела бы смысл только у части категорий, и за этим пришлось бы следить.

- **Платье и комбинезон** (`dress`, `jumpsuit`) закрывают верх и низ сразу, правила должны это учитывать.
- **Костюма как категории нет.** Пиджак и брюки носят и по отдельности, поэтому это две вещи — иначе брюки не предложить со свитером.
- **Аксессуары, которые участвуют в правилах, — отдельные категории:** `umbrella` для дождя, `sunglasses` для солнца, `hat` и `scarf` для холода. Всё остальное — `accessory`. Очки именно солнцезащитные: обычные по погоде не выбирают.
- **Термобельё** (`thermal`) есть: это нижний слой, и правилу «температура → слои» оно важно. **Обычного нижнего белья нет**: по погоде его не подбирают, а онбординг от него только длиннее.
- **Купальника нет:** утренняя рекомендация по погоде его не предложит. Появится вместе с уточнением запроса вроде «иду на пляж», одной категорией `swimwear`.

### Защита от погоды — свойство, а не категория

Непромокаемость — поле `Waterproof`, а не категория «для дождя». Дождевик по месту в образе — верхняя одежда. Выдели его в отдельную категорию, и рекомендатель не поймёт, что он взаимозаменяем с курткой, и может предложить оба. А свойство бывает у вещей разных категорий — дождевик, резиновые сапоги, — и одно правило покрывает их все.

По той же схеме добавится защита от ветра, когда появится правило про ветер.

### Цвета

- **Своя короткая палитра, а не тип из библиотеки.** Цвет пользователь выбирает кнопкой, точного оттенка нет и не будет, а правила сочетания формулируются по названиям. К тому же `domain/` не импортирует сторонних пакетов. Когда цвет начнут определять по фото, перевод «RGB → ближайшее название» будет жить в адаптере или в vision.
- **Палитра короткая, потому что правила сочетания растут примерно как квадрат её размера.** Цвета делятся на нейтральные (чёрный, белый, серый, бежевый, тёмно-синий — сочетаются со всем) и акцентные; правила пишутся только для акцентных.
- **Синий, голубой и тёмно-синий — разные цвета.** В русском голубой — не оттенок синего, а тёмно-синий ведёт себя как нейтральный. Граница для пользователя размыта, поэтому соседние оттенки правила считают совместимыми.
- **Главный цвет — отдельное поле, а не «первый в списке».** Для сочетания важен доминирующий цвет: белая футболка с красным принтом — белая. Договорённость о порядке ничем не защищена, а поле видно сразу. Главный и дополнительные цвета собраны в структуру `Colors`, потому что у пары свои правила: главный обязателен, не повторяется среди дополнительных, дублей нет.

### Уровень теплоты, а не диапазон температур

`WarmthLevel` — уровень от 1 до 5, а не «от скольких до скольких градусов». Диапазон у одной вещи не определён: футболка сама по себе — от +20, а под пуховиком годится и в −15. Правилу слоёв нужно знать, сколько тепла вещь добавляет. И пользователь при онбординге не ответит, при скольких градусах носит кофту, а «лёгкая» или «тёплая» выберет сразу.

| Уровень | Примеры | Внешним слоем |
|---|---|---|
| 1 — лёгкая | футболка, шорты, сандалии | от +20 °C |
| 2 — средняя | лонгслив, джинсы, ветровка | от +10 до +20 °C |
| 3 — тёплая | свитер, демисезонная куртка | от 0 до +10 °C |
| 4 — зимняя | зимняя куртка, шерстяная шапка | от −10 до 0 °C |
| 5 — для мороза | пуховик, ботинки на меху | ниже −10 °C |

Температуры — ориентир для выбора уровня, а не правило: раскладка по слоям живёт в `domain/rules/`.

- **Пять уровней, а не три или четыре:** для российской зимы «ниже нуля» слишком широко, зимняя куртка и пуховик должны различаться.
- **Число, а не строка:** уровни упорядочены, правила сравнивают «теплее» и «холоднее».
- **Значения заданы явно, а не через `iota`:** их нельзя случайно перенумеровать, а ноль означает забытое поле.
- **Уровень обязателен только для одежды:** у зонта, очков, сумки и прочих аксессуаров теплоты нет, уровень у них нулевой. `HasWarmth` перечисляет исключения, а не одежду: новая категория одежды получит уровень теплоты по умолчанию.

### Значения статуса

Почему статус — перечисление, объяснено в разделе 5. Почему значения такие:

- **«Грязная», а не «в стирке».** Это состояние вещи, а не процесс, и оно покрывает всё сразу: корзину, машинку, сушку. Бот сможет сам ставить его после «надел» — а «надел → в стирке» он утверждать не может.
- **«В архиве», а не «потеряна».** Покрывает и «потерял», и «продал», и «отдал». Архивная вещь хранится, пока пользователь сам не удалит её из архива. Автоматической очистки нет, поэтому не нужны ни задача в планировщике, ни колонка `archived_at`. Архивные вещи входят в лимит вещей: когда он достигнут, место освобождается удалением из архива. Что делать при удалении со ссылками из `outfit_items` — удалять вместе с вещью или обнулять — решается в миграции. Решение предварительное.
- **«Не по сезону» — не статус, а вычисляется.** Вещь не по сезону, если среди её сезонов нет текущего. Статусом это было раньше и повторяло поле «Сезоны». Хранить это в статусе нельзя: вещь бывает грязной и не по сезону одновременно, а записанное значение устаревало бы при каждой смене сезона и правке вещи. Статус — только то, что знает человек.
- **Сезон — по календарю северного полушария** (`SeasonAt`): тёплый сентябрь всё равно осень. Температуру в подборе учитывает уровень теплоты, сезоны там — фильтр. Граница сезона пока по времени сервера; когда появятся часовой пояс и место пользователя, считать будем по ним.

### Создание и проверка вещи

Невалидная вещь не должна появляться вовсе. Проверяет её `Validate`: его вызывает конструктор `NewItem`, а адаптер Postgres — при чтении из базы.

- **Параметры конструктора — структурой `NewItemParams`, а не списком аргументов.** В месте вызова каждое значение подписано именем поля, и два значения одного типа не перепутать местами. `ID` и `Status` в параметрах нет: `ID` выдаёт база, а новая вещь всегда доступна. Слабость приёма — забытое поле молча становится нулевым. Её закрывает то, что нулевые значения у нас невалидны: пустая строка, ноль у владельца и у теплоты одежды. Функциональные опции (`WithName(...)`) не подходят: они для необязательных настроек, а у вещи почти все поля обязательны.
- **`Validate() error`, а не `Valid() bool`.** По `bool` не понять, что именно не так. Проверка собирает все проблемы в одну ошибку, чтобы не исправлять их по одной. У перечислений остаётся `Valid() bool`: там проблема всегда одна — неизвестное значение.
- **Ошибка оборачивает `ErrInvalidItem` через `%w`.** Снаружи её распознают через `errors.Is`, а не сравнением текста. Текст проблем — для лога, не для пользователя: неизвестная категория — ошибка в коде, а не человека. Если понадобится подсказать пользователю конкретное поле, заводятся отдельные ошибки вроде `ErrEmptyItemName`.
- **Ошибка лежит рядом с кодом, который её возвращает**, а не в общем `errors.go`. Отдельный файл оправдан для ошибок, общих для нескольких файлов пакета, но не как свалка «все ошибки к ошибкам».
- **Хотя бы один сезон обязателен.** Вещь без сезонов молча выпадала бы из подбора. Всесезонной вещи бот ставит все четыре.
- **Сезоны и дополнительные цвета — срезы, а не `map`.** Map исключила бы повторы, но перебирается в случайном порядке — сезоны в карточке вещи каждый раз стояли бы по-разному, — а запись в незаполненную map роняет программу. Повтор может прийти только из ошибки в коде бота, и `Validate` его ловит.
- **Проверки на количество сезонов и цветов нет.** Она следует из двух других: значения известные и не повторяются, значит, больше, чем есть в палитре, не набрать. Осмысленным был бы только продуктовый потолок, например на число дополнительных цветов, и обосновывать его нужно правилами сочетания.

## 7. Mini App для гардероба

Добавление и просмотр вещей — в Telegram Mini App на React, а не в диалоге из сообщений.

### Почему не чат

У вещи восемь полей, три из них — с выбором нескольких значений. Через сообщения это шесть-семь шагов диалога, и ошибка на пятом шаге заставляет пройти всё заново. Форма — один экран, и на нём же удобно показать сотню вещей с фильтрами.

Чат остаётся для быстрых действий одной кнопкой: утренняя рекомендация, фидбек, «пометить грязной».

### Как приложение связано с Go

- **HTTP API, а не `sendData`.** `sendData` работает только с кнопками клавиатуры, ограничен 4 КБ и закрывает приложение. API позволяет загрузить список вещей, показать ошибку под полем и не закрываться.
- **Серверная часть — `internal/telegram/miniapp/`, рядом с хендлерами бота.** Технически это другое: не апдейты и сообщения, а JSON-запросы со страницы. Но структура группирует код по смыслу, а по смыслу Mini App — тот же UI в Telegram: вне его страница не открывается, а пользователя API узнаёт по подписи Telegram. Сервисы вызываются те же, что из хендлеров бота.
- **Код страницы — в `frontend/` в корне репозитория.** Это отдельный проект со своей сборкой и зависимостями, внутри `backend/` ему не место.
- **Пользователь определяется по `initData`.** Telegram подписывает эти данные токеном бота, сервер проверяет подпись. `user_id` без проверенной подписи не принимается: подставить его может кто угодно.
- **Один процесс, один HTTP-сервер** обслуживает вебхук, API и статику приложения.
- **Привязка к Telegram держится в одном месте.** На сервере про Telegram знает только проверка `initData`: она превращает запрос в `user_id`, а обработчики дальше работают только с ним. Во фронтенде обращения к Telegram SDK собраны в одном модуле. Если понадобится веб-версия вне Telegram, заменить придётся вход, а не всё приложение.

### Как это соотносится с разделом 1

Бот выбран на Go, чтобы UI и логика жили в одном языке и сущности не расходились. С Mini App часть UI уходит в JS, и перечни категорий и цветов могут разъехаться. Поэтому списки для формы — категории, цвета, сезоны, уровни теплоты вместе с подписями — приложение получает из API. Источник у них один: домен.

## 8. Подбор образа

Правила — в `domain/rules/`, сценарий — в `service/recommender.go`.

### Погода и город

- **Open-Meteo.** Бесплатно, без ключа, в одном месте прогноз по часам и поиск городов с часовым поясом. Адаптер `adapter/openmeteo` сводит часы в `domain.Weather`: минимум и максимум, наибольшую вероятность осадков, ветер, УФ-индекс. Пороги вроде «дождь — от 50 %» живут в правилах, а не в адаптере: это решение о подборе, а не о формате провайдера.
- **Город вводится вручную** и хранится в `locations`, геолокация — следующим шагом. Координаты и пояс приходят от клиента. Пользователя гарантирует подпись initData, а подменив координаты, человек навредит только себе. От мусора защищает `Validate`, в том числе от неизвестного пояса.
- **Часы — с текущего до 22:00 по времени города**, поздно вечером — хотя бы три ближайших. Образ, выбранный утром, должен подойти и вечером, а не только в текущий час.
- **День, сезон и история считаются по поясу города**, не сервера. База поясов встроена в бинарник (`time/tzdata`), иначе в контейнере без неё города не нашлись бы.
- **Кэша погоды пока нет.** Все варианты образа приходят одним ответом, и «Другой вариант» погоду заново не запрашивает. Кэш понадобится утренней рассылке, когда запросы пойдут пачкой.

### Как собирается образ

- **Теплота — по самой холодной части дня** по ощущаемой температуре. Куртку днём можно снять, а замёрзнуть утром без неё нельзя. Если днём теплеет до +20, образ об этом предупреждает.
- **Слои.** Верхняя одежда нужна ниже +15 по ощущениям, её уровень равен уровню погоды. Верх под ней — на уровень легче. Верх не теплее «тёплого», низ не теплее «зимнего»: в мороз греют верхняя одежда и термобельё. Шапка и шарф — с уровня «зимняя», термобельё — в мороз, носки — везде, кроме жары.
- **Перебор, а не выбор по одной вещи.** Каждое сочетание основы (верх и низ, платье или комбинезон), верхней одежды и обуви получает штрафы: за каждый уровень теплоты мимо нужного, за промокающую вещь в дождь, за цвета, за недавнее ношение. Лучший образ — с наименьшей суммой. Выбор по одной вещи не учёл бы цвета: лучший верх может не сочетаться ни с одним низом. На сотне вещей перебор занимает миллисекунды.
- **Нет подходящей вещи — образ всё равно собирается** из самой близкой по теплоте, с заметкой «легче, чем нужно». Пустой ответ бесполезнее образа с предупреждением.
- **Варианты отличаются одеждой.** Для каждой основы остаётся лучший набор, поэтому «Другой вариант» — это другой верх или низ, а не те же вещи с другой обувью.
- **Дождь.** Зонт — если он есть и ветер слабее 11 м/с. Иначе непромокаемая верхняя одежда, даже когда тепло. Если нет ни того, ни другого, образ предупреждает. В снег зонт не предлагается.
- **Солнце.** Очки — с УФ-индекса 3 без осадков, лёгкий головной убор — с 6.
- Недоступные и не сезонные вещи в подбор не попадают.

### Цвета

Правила пишутся для семей акцентных цветов, нейтральные сочетаются со всем (раздел 6). Один акцент — без штрафа, два — небольшой штраф. Спорящая пара — заметный: красный с оранжевым, розовым или зелёным, оранжевый с розовым или фиолетовым. Три акцента и больше — большой. Это штраф, а не запрет: из пяти вещей образ соберётся и так.

### История: «не повторяться»

- **Надетое записывается только кнопкой «Надеваю»**, а не при показе образа: рекомендация — не факт ношения (раздел 5).
- **Образ дня один.** Повторное «Надеваю» заменяет его: человек передумал — в истории остаётся то, что он надел.
- **Надетый образ виден на главном экране**, в списке гардероба у его вещей метка «Надето», а в подборе совпадающий вариант отмечен так же. Это не статус, по той же причине, что и «не по сезону» (раздел 6): знание уже лежит в образе дня. API отдаёт только ID вещей: сами вещи у приложения уже загружены, и карточка сразу показывает их правки и удаление.
- **Штраф за одежду, надетую за последние 7 дней:** вчерашняя — большой, недельной давности — маленький. Обувь, куртку и сумку носят каждый день, их история не штрафует. Сегодняшний образ тоже не штрафуется, иначе после «Надеваю» подбор предложил бы другое.
- Глубина истории пока константа. Настройкой она станет вместе с остальными настройками пользователя.

### Тексты

Домен отдаёт заметки кодами, по-русски их пишет `telegram/texts`, как и подробности погоды. Те же тексты понадобятся утренней рассылке в чате.
